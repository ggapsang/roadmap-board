# WOLFPACK — 개발 방향 점검: 순서 기반 이벤트 전개 시스템 정합성

WOLFPACK은 **순서 기반 이벤트 전개 시스템**의 첫 활용 예다.
(근거 문서: `refs/TTB-만들어진 배경-*.pdf`, `refs/TTB-순서 기반 이벤트 전개 시스템 - 개발자를 위한 설명-*.pdf`)

지금의 로드맵 보드는 그 일반형에 **"달력 눈금을 쓰고, 트랙은 과제이며, 관계는 선행이고,
보드는 하나"** 라는 설정값을 박은 상태다. 이 문서는 그 관점에서 현재 코드가 어긋나거나
앞으로의 확장을 막는 지점을 정리한 목록이다. 구현 계획이 아니라 **지켜야 할 방향**과,
지금 의식해 두면 나중이 쉬워지는 우선순위다.

> **판단 기준 (설명 문서 §6·§8)**
> *이것은 이 보드에서만 성립하는가, 아니면 이벤트 자체에 성립하는가?*
> 보드에서만 성립 → **배치·표시**. 이벤트 자체에 성립 → **이벤트·관계**.
> 애매하면 **표시 쪽**에 둔다. 표시를 나중에 본질로 올리는 건 쉽지만, 반대는 데이터를 쪼개는 일이다.

## 5요소 대응 (시스템 개념 ↔ 현재 코드)

| 시스템 개념 | 현재 WOLFPACK | 위치 |
|---|---|---|
| **이벤트** — 앞뒤 관계를 가진 단위. 접으면 카드, 펼치면 보드 | `item` | `src/core/schema.js`, `db/repository.js` |
| **트랙** — 이벤트가 흐르는 갈래 | `tracks[]` | `schema.js`, `ui/board/head.js` |
| **관계** — 선행·합류·원인·참조. 보드를 넘나드는 독립 대상 | `item.dp[]` (선행만, 카드의 속성) | `item.dp`, DB `dependency` |
| **순서/시간** — 앞뒤 관계. 달력은 선택적 눈금 | 항상 달력축, `dayIndex`로 위치 계산 | `core/timescale.js`, `core/layout.js` |
| **태스크** — 순서 없이 카드에 담기는 할 일 | `item.tasks[]` | `schema.js`, DB `task`, `ui/panels/item.js` |

## 이미 지켜 온 것 (정합)

- **문서 상태(Store) ↔ 화면 상태(ViewState) 분리** — 저장·되돌리기 경계.
  단, ViewState는 세션 뷰(필터·검색·배율·선택)이지 "보드별 배치"는 아니다(→ 아래 1번).
- **사용자가 정하는 것을 코드에 안 박음** — 트랙 구성·담당 조직은 문서 안에 있고 보드에서 편집.
- **색은 상태 시맨틱** — 트랙별 임의 색 없음.
- **마일스톤 = 시점 이벤트 / 기간 마일스톤 = 기간 이벤트** — 같은 단위, 배치만 다름(최근 반영).
- **중첩(container/child)** — "이벤트가 자식을 가질 수 있는 자리"의 절반(하위 카드).

## 수정·정비 목록

우선순위는 **"나중에 추가하기 어려운 것 먼저"** 순이다. 지금 당장 큰 리팩터가 필요한 건 아니지만,
새 기능·필드·관계를 넣을 때마다 아래를 막지 않는지 확인한다.

### 1. 본질(이벤트)과 배치(표시)를 나눠 둔다 — 최우선 ✅ (1차 완료)
- **근거**: 설명 §3.5·§6.1·§6.5 ("나중에 추가하기 가장 어려운 부분").
- **한 일**: 배치·표시 필드(`t, sp, x, w, hd, align, showNote`)를 `item.place`로 모아 이벤트 본질과 분리했다. `schema.js`(v8·v9·v10 마이그레이션 + normalize), `repository`(place ↔ 컬럼), 렌더러·드래그·패널 전부 `item.place.*`를 쓴다. 3단계로 나눠 커밋, 스모크 30단계 검증.
- **남은 방향**: 아직 `place`가 하나(보드 하나)다. 두 번째 보드가 오면 `item.place` → `placements[boardId]`로 확장(지역 변경). 나아가 이벤트 본질을 보드-독립 테이블로 빼는 것(#3)과 이어진다.
- **규칙**: 새 필드는 §6 기준으로 본질/배치를 정하고, 배치성이면 `place`에 넣는다.

### 2. 관계를 이벤트와 동등한 일급 객체로 ✅ (선행·포함 완료)
- **근거**: §3.6·§6.3·§6.7.
- **한 일**: `item.dp`(선행)·`item.parent`(포함)를 문서 레벨 `doc.relations: [{id, type, from, to}]`로 노출했다. 종류(`type`)는 `config.RELATION_TYPES`(dep·contain·…)로 확장(코드에 안 박음). `schema`의 `normalizeRelations`가 종류 허용·끝점 존재·자기순환·중복·**순환 금지 종류의 사이클 차단**(#5·#7)을 한 곳에서 검증. `dep`은 arrows·패널·삭제·복제·`repository`(dependency 테이블)가 직접 쓴다.
- **포함(contain) 방식**: `item.parent`가 레이아웃에 깊어(childrenOf·중첩 렌더) **렌더러는 `item.parent`를 그대로 두고**, contain 관계는 정규화·로드 시 `item.parent`/`parent_id`에서 만들어 `doc.relations`에 노출한다(회귀 0, 이식·검증은 관계로). 완전 이관(childrenOf를 관계에서)은 다중 소속(§3.2)이 필요해질 때.
- **남은 방향**: 다른 종류(합류·원인·참조)는 config에 자리만. 여러 종류가 실제로 생기면 DB에 `relation(type)` 테이블로 일반화.

### 3. 이벤트에 보드-독립 식별자 ✅ (기반 완료)
- **근거**: §6.2.
- **한 일**: 관계·배치는 이미 `item.id`(정렬 순번 `ord`가 아니라)를 키로 참조한다 — 보드-의존 식별을 관계 키로 쓰지 않는다. 남은 위험은 **복제·반입으로 같은 id가 여러 보드에 흩어지는 것**(서로 다른 이벤트가 같은 키). 이를 원천에서 막게 `schema.reidentify(doc)`를 두고 `repository.duplicateProject`가 복제본에 새 이벤트 id를 부여한다(상위 일정·관계·태스크 참조 함께 이동). 스모크 `id` 단계(전부 새 id·유일·참조 정합·관계 보존).
- **남은 방향**: "같은 이벤트가 **여러 보드에 동시에**"는 아직 없다(다중 보드 자체가 미구현, §8). 그 기능이 오면 이벤트 본질을 보드-독립 테이블로 빼고 배치는 `placements[boardId]`(#1)로 — 지금 식별이 보드-독립적이라 그때 데이터를 쪼갤 일은 없다.

### 4. 순서를 1차로, 달력을 선택적 눈금으로 — (a)(b)(c) 초안 완료 ✅
- **근거**: §3.1·§6.4·§8.
- **현재**: 축은 항상 달력. `TimeScale`·`layout`이 `s·e`(날짜)와 `dayIndex`로만 위치를 계산해 **날짜 없는 보드가 불가능**하다.
- **(a) 씨앗 ✅**: `meta.display.axis`(calendar|order)·`axisDir`(vertical|horizontal)를 표시 설정으로 넣고(검증 포함), `TimeScale`을 "달력 스케일"로 문서화. `Board#buildScale`이 스케일 교체 지점(yOf/span/dayAt/height 인터페이스)임을 명시 — 나머지 코드는 '달력'을 몰라도 된다.
- **(b) ✅**: `src/core/order.js`의 `computeOrder(items, relations)` — 선행 그래프의 위상 순위(rank)를 낸다. 순수 함수, 순환 안전. 관계선 없는 이벤트는 동시적(같은 rank 가능). 달력 모드에선 아직 안 쓰고, 순서 모드(c)가 소비한다.
- **(c) 초안 ✅**: `axis === 'order'`면 rank로 배치·렌더하는 **순서 보드**(날짜 없음). 카드는 스케일(`TimeScale`/`OrderScale`)의 `topOf/heightOf`만 쓰므로 달력을 모른다. 왼쪽 축은 순번, 같은 트랙·같은 rank는 레인 분할, 화살표는 그대로. **달력 경로는 한 줄도 안 바뀜**(전부 `axis==='order'` 분기로 격리). 구성 › 표시에서 토글. 초안 한계: 중첩은 펼쳐서 다룸, 순서 모드에선 드래그·생성·달력칸 편집 꺼짐, 카드 높이 고정(내용 많으면 좁음). 다음: 순서 모드 드래그로 재정렬, 중첩 유지, 카드 크기.

### 5. 관계 종류별 구조 규칙 검증을 한 곳에 ✅ (핵심 완료)
- **근거**: §6.7.
- **한 일**: 모든 관계 검증이 `schema.normalizeRelations` **한 곳**에 모였다. 종류별 규칙은 `config.RELATION_TYPES`의 플래그로 켠다 — 지금은 `acyclic`(순환 금지 DAG)이 있고 선행·포함이 이를 쓴다. 끝점 존재·자기순환·중복도 여기서 본다. 종류가 늘어도 이 함수에 규칙만 더한다.
- **남은 방향**: 합류=트리(대상 하나)·참조=순환 허용 규칙은 **그 종류가 실제로 생길 때** 추가한다(지금 만들면 만들 수 없는 관계를 검증하는 죽은 코드 — §8). 플래그 자리는 이미 있다.

### 6. 태스크(순서 없는 포함) ✅
- **근거**: §3.3·§6.6.
- **한 일**: 카드가 **순서 없는 태스크**(`item.tasks: [{id, text, done}]`)를 담는다. 5요소 중 마지막이던 "태스크"가 자리를 얻었다. 이벤트 본질이라 `place`가 아니라 `item`에 직접 둔다. `schema`(v12_to_v13 + normalize, 태스크 id는 보드 전체 유일), `repository`(`task` 테이블, item CASCADE), item 패널(추가·완료·삭제), 카드 칩(`☑ done/total`). 스모크 `task` 단계(칩·정규화 라운드트립·id 유일·DB 왕복).
- **남은 방향**: 태스크끼리 앞뒤(순서)가 생기면 **하위 카드로 승격**(같은 단위, "순서축 위에 놓이는가"만 다름) — 승격 동작은 아직 수동(패널에서 새 일정으로). 드래그 재정렬은 순서 없는 목록이라 불필요.

### 7. 카드↔보드 펼침·드릴다운 재귀 여지
- **근거**: §6.6·§8.
- **현재**: 중첩 컨테이너는 있으나 "카드를 펼쳐 하나의 보드로", "트랙을 펼쳐 그 안 흐름을", 드릴다운/브레드크럼은 없다.
- **방향**: 지금 구현 안 해도 되나, **한 문법(순서축·트랙·관계선)이 모든 층위에 같게 적용**되는 전제를 깨지 않는다.

### 8. 지금은 "막지만 않으면" 되는 것
다중 보드 전환, 보드 간 영향 전파(선행 지연이 보드를 넘어 퍼지기), 보드별 공유 범위(별칭·표시 방식), 축 방향 전환.
지금 내리는 구조적 결정이 이것들을 **불가능하게 만들지 않도록** 한다.

## 요약

- **나중에 추가하기 비싼 기반은 모두 놓았다.** 본질/배치 분리(#1)·관계 일급화(#2)·보드-독립 식별(#3)·순서 스케일 초안(#4)·관계 검증 일원화(#5)·순서 없는 태스크(#6). 5요소(이벤트·트랙·관계·순서·태스크)가 전부 코드에 자리를 얻었다.
- **남은 것은 대부분 "미루기 싼" 표시·UX다.** 순서 모드 상호작용(드래그 재정렬·중첩 유지·카드 크기), 카드↔보드 드릴다운(#7), 다중 보드(#8)는 데이터 모델을 흔들지 않고 나중에 얹을 수 있다 — 기반이 이미 그것들을 막지 않는다.
- 새 기능·필드·관계를 넣을 때마다 §6 판단 기준(본질이냐 표시냐)을 적용하고, 위 기반을 되돌리는 결정을 피한다.
