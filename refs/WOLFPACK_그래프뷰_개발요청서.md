# WOLFPACK 그래프 뷰 개발 요청서

순서 기반 이벤트 전개 시스템 · 표현 층 기능 · 2026-09

---

## 0. 이 문서의 지위와 범위

이 문서는 시스템 전체를 하나의 그래프로 보여 주는 **그래프 뷰**의 개발 요청서다. 「WOLFPACK 개발 규칙」을 전제로 하며, 둘이 충돌하면 개발 규칙을 따른다.

- 요구사항은 **금지 목록(2장)** 으로 정리한다. 금지 목록에 없는 구현 선택은 개발자 재량이다.
- 금지 목록을 지키면서 구현 비용이 크다고 판단되면, 우회하지 말고 먼저 묻는다.
- 3장은 계산 방식의 정의, 4장은 예상 이슈와 대안이다. 4장의 대안은 제안이며, 채택 여부는 협의한다.
- 그래프 뷰는 **표현 층의 기능**이다. 이 기능 때문에 이벤트, 포함, 배치, 관계의 구조가 바뀌어서는 안 된다.

1차 범위는 **읽기 전용 탐색**이다. 그래프 뷰에서의 편집은 범위 밖이다(6장 열린 질문 참조).

## 1. 기능 정의

그래프 뷰는 모든 이벤트를 노드로, 모든 관계를 엣지로 그리는 힘 기반(force-directed) 그래프다. 옵시디언 그래프 뷰와 같은 물리 시뮬레이션을 쓰되, 관계 종류에 따라 **방향 중력**이 작용하여 무작위 배치가 아니라 시스템의 구조를 스스로 드러내는 배치로 수렴한다.

| 구성 요소 | 정의 |
|---|---|
| 노드 | 이벤트 하나 = 노드 하나. 모양은 모두 원 |
| 노드 크기 | 포함 관계를 따라 내려가며 도달하는 **중복 없는 하위 이벤트 수**의 제곱근에 비례 |
| 엣지 | 관계 하나 = 엣지 하나. 굵기는 모두 같음 |
| 구조 중력 | 포함 엣지에 작용. 부모가 위, 자식이 아래로 가려는 힘 |
| 흐름 중력 | 선행·합류·원인 엣지에 작용. 앞선 쪽이 왼쪽, 뒤따르는 쪽이 오른쪽으로 가려는 힘 |
| 참조 | 방향 중력 없음. 약한 스프링만 |
| 상호작용 | 노드 끌기, 호버 시 이웃 강조와 관계 라벨 표시, 구조·흐름 중력 세기 조절, 확대·이동 |

결과적으로 화면의 **세로는 소속의 깊이, 가로는 순서**로 읽힌다. 두 중력을 모두 0으로 두면 순수한 힘 기반 배치(옵시디언과 동일)가 된다.

## 2. 금지 목록

### 2.1 층과 데이터

**G-01. 그래프 뷰에서 이벤트, 포함, 배치, 관계를 생성·수정·삭제하지 않는다.**
1차 범위는 읽기 전용이다. 노드를 끌어 다른 노드에 놓았을 때 포함이나 관계가 생기는 동작을 만들지 않는다.

**G-02. 그래프 뷰 전용의 데이터 사본이나 별도 스키마를 두지 않는다.**
그래프는 이벤트·포함·관계 저장소에서 매번 유도한다. 별도 사본을 두면 반드시 원본과 어긋난다.

**G-03. 노드 좌표를 이벤트에 저장하지 않는다. 배치에도 저장하지 않는다.**
배치는 "어떤 포함 관계 위에 어떻게 놓였는가"의 표시 정보다. 그래프 뷰의 좌표는 어떤 포함 관계에도 속하지 않으므로 배치가 아니다. 좌표 저장이 필요하면 별도의 뷰 상태로 둔다(4.7).

**G-04. 노드 크기의 근거값(하위 이벤트 수)을 이벤트 속성으로 저장하지 않는다.**
이 값은 포함 관계에서 계산되는 파생값이다. 캐시는 허용하지만 이벤트 본질이 아니다.

**G-05. 그래프 뷰 상태(좌표, 중력 설정, 확대 배율)를 협업 공유 문서에 넣지 않는다.**
한 사용자가 노드를 끌 때 다른 사용자의 화면이 움직여서는 안 된다.

### 2.2 노드

**G-06. 한 이벤트를 두 개 이상의 노드로 그리지 않는다.**
부모가 둘인 이벤트도 노드는 하나다. 분신, 복제, 별칭 노드를 만들지 않는다. 다중 소속은 한 노드에 포함 엣지가 둘 들어오는 것으로 표현되고, 구조 중력이 그 노드를 두 부모 아래 적절한 위치로 옮긴다.

**G-07. 역할 이름(보드, 트랙, 카드, 태스크)으로 노드의 색, 모양, 크기를 나누지 않는다.**
그래프 뷰 코드 안에 "이 이벤트가 트랙인가"를 판정하는 분기가 있으면 규칙 위반이다. 같은 이벤트가 어떤 보드에서는 트랙이고 다른 보드에서는 카드이므로, 그래프 뷰에서 역할은 정의되지 않는다.

**G-08. 노드 모양을 종류별로 다르게 하지 않는다.**
모든 노드는 원이다. 크기 외의 시각 속성(색)은 상태 표시 등 별도 요구가 확정될 때까지 한 가지로 둔다. 선택·호버 강조만 예외다.

### 2.3 노드 크기

**G-09. 직접 연결 수(차수)로 크기를 정하지 않는다.**
차수는 포함 선과 흐름 선을 같은 1로 더한다. 두 관계는 층이 다르므로 합산값은 의미가 없다. 또 차수 방식에서는 트랙이 가장 크고 보드가 작게 나오는 역전이 생긴다.

**G-10. 포함 이외의 관계를 크기 계산에 넣지 않는다.**
선행, 합류, 원인, 참조는 크기와 무관하다. 흐름의 허브 여부는 호버 강조로 보여 준다.

**G-11. 경로 수로 세지 않는다.**
다중 소속 때문에 한 이벤트가 여러 경로로 도달할 수 있다. 같은 이벤트는 한 번만 센다.

**G-12. 한 단계 자식 수만 세지 않는다.**
포함을 끝까지 따라 내려간 전체 하위 이벤트 수를 센다. 순서 있는 포함과 순서 없는 포함을 구분하지 않는다.

**G-13. 하위 이벤트 수에 반지름을 선형 비례시키지 않는다.**
하위가 수백 개인 이벤트가 화면을 덮는다. 제곱근으로 누르고 상한을 둔다(3.1).

### 2.4 엣지

**G-14. 관계 종류를 선 굵기나 미세한 파선 패턴으로 구분하지 않는다.**
굵기는 모든 엣지가 같다. 구분은 색 계열 네 가지로만 한다.

| 계열 | 해당 관계 | 표현 |
|---|---|---|
| 포함 | 순서 있는 포함, 순서 없는 포함 | 회색 실선 + 작은 화살촉 (부모 → 자식) |
| 흐름 | 선행, 합류 | 흐름색 실선 + 작은 화살촉 |
| 원인 | 원인 | 원인색 실선 + 작은 화살촉 |
| 참조 | 참조 | 연한 점선 + 작은 화살촉 |

순서 있는 포함과 순서 없는 포함, 선행과 합류는 선으로 구분하지 않는다. 필요한 경우 호버 라벨로 구분한다.

**G-15. 포함 엣지의 방향을 위치에만 맡기지 않는다. 화살촉을 단다.**
구조 중력은 최소 간격에 못 미칠 때만 밀어내는 힘이므로(G-20), 노드가 복잡하게 얽히거나 사용자가 끌어 놓으면 다른 힘과의 상호작용으로 부모가 자식보다 아래에 놓일 수 있다. 위치만으로는 방향을 보장할 수 없으므로 부모에서 자식으로 향하는 화살촉을 단다.

**G-16. 관계 라벨을 상시 표시하지 않는다.**
라벨은 호버하거나 선택한 노드에 연결된 엣지에만 글자로 표시한다.

**G-17. 같은 두 이벤트 사이의 여러 관계를 선 하나로 합치지 않는다.**
관계는 독립 대상이다. 관계가 둘이면 선도 둘이며, 겹치지 않도록 곡선으로 벌려 그린다.

### 2.5 중력과 물리

**G-18. 참조에 방향 중력을 걸지 않는다.**
참조는 순환을 허용한다. 순환이 있는 관계에 방향 중력을 걸면 힘이 서로 싸워 수렴하지 않는다.

**G-19. 순환에 속한 엣지에 방향 중력을 걸지 않는다.**
관계 종류별로 순환이 금지되어 있어도, 흐름 계열(선행·합류·원인)을 합친 그래프에서는 순환이 생길 수 있다(4.1). 순환에 속한 엣지는 그 순간 방향 중력에서 제외한다.

**G-20. 방향 중력을 목표 좌표로 끌어당기는 방식으로 구현하지 않는다.**
방향 중력은 "최소 간격에 못 미칠 때만 밀어내는 힘"이다. 부모를 특정 y값에 고정하거나 순서 순위로 x값을 고정하면 힘 기반 배치가 아니라 계층형 배치가 되어, 이 기능의 목적이 사라진다.

**G-21. 방향 중력 설정을 코드 곳곳에 상수로 흩어 두지 않는다.**
관계 종류별 방향, 최소 간격, 세기는 관계 종류 설정 한 곳에서 관리한다. 개발 규칙 8의 "관계를 검증하는 지점은 한 곳"과 같은 원칙이다.

**G-22. 무작위 초기 배치를 쓰지 않는다.**
같은 데이터를 열면 같은 배치가 나와야 한다. 초기 좌표는 구조에서 결정적으로 계산하고, 필요한 흔들림은 고정 시드 난수로 준다(3.3).

**G-23. 시뮬레이션을 영구히 돌리지 않는다.**
수렴하면 멈춘다. 끌기, 데이터 변경, 중력 조절 시에만 다시 가열한다.

**G-24. 매 프레임 DOM 요소를 새로 만들지 않는다.**
요소는 한 번 만들고 좌표 속성만 갱신한다.

**G-25. 노드 수가 수백 개를 넘는 상황에서 모든 쌍의 반발력을 직접 계산하지 않는다.**
Barnes-Hut 근사를 쓴다(4.2).

### 2.6 상호작용

**G-26. 노드를 끌어 놓는 것으로 어떤 데이터도 바뀌지 않는다.**
G-01의 재확인이다. 끌기는 시뮬레이션 안의 일시적 고정일 뿐이다.

**G-27. 중력 세기를 고정값으로 두지 않는다.**
구조 중력과 흐름 중력을 각각 조절할 수 있어야 하고, 0이면 해당 방향 중력이 완전히 꺼져야 한다.

**G-28. 호버 강조가 배치를 바꾸지 않는다.**
호버는 색과 불투명도만 바꾼다. 노드를 끌어당기거나 확대하지 않는다.

## 3. 계산 정의

### 3.1 노드 크기

**정의**: 이벤트 e의 하위 수 `d(e)`는 포함 관계를 부모에서 자식 방향으로 따라가며 도달할 수 있는 이벤트의 집합의 크기다. e 자신은 제외한다. 순서 있는 포함과 순서 없는 포함을 모두 따라간다.

**반지름**: `r(e) = min(r_max, r_min + k × √d(e))`

기본값 제안은 `r_min = 5`, `k = 3`, `r_max = 40`이다. 조정 가능한 설정으로 둔다.

**계산 방법**: 포함은 DAG이므로 자식이 먼저 오는 위상 순서로 한 번 훑으며 집합을 합친다.

```
order ← 포함 그래프의 역위상 순서 (자식이 부모보다 먼저)
for e in order:
    desc[e] ← 빈 비트셋
    for c in children(e):
        desc[e] ← desc[e] ∪ {c} ∪ desc[c]
    d(e) ← popcount(desc[e])
```

**예시** (핵심정리 문서의 예시 이벤트 기준)

| 이벤트 | 하위 이벤트 | d | r |
|---|---|---|---|
| 1차년도 | 요구사항 1, 요구사항 2, 설비 설치, 현장 검증, 모니터링 화면, 도면 확인, 반입 일정 | 7 | 12.9 |
| 요구사항 1 | 설비 설치, 현장 검증, 도면 확인, 반입 일정 | 4 | 11.0 |
| 에이텍오토 작업 | 설비 설치, 도면 확인, 반입 일정 | 3 | 10.2 |
| 설비 설치 | 도면 확인, 반입 일정 | 2 | 9.2 |
| 요구사항 2 | 모니터링 화면 | 1 | 8.0 |
| 그 외 | 없음 | 0 | 5.0 |

설비 설치는 요구사항 1과 에이텍오토 작업 양쪽의 하위에 모두 한 번씩 세어지지만, 1차년도에서는 한 번만 세어진다. 이것이 G-11이 요구하는 동작이다.

### 3.2 방향 중력

관계 종류별로 방향 벡터 `u`, 최소 간격 `gap`, 세기 `s`를 설정한다. 엣지의 출발을 a, 도착을 b라 할 때, a에서 b로의 변위를 u 방향으로 사영한 값이 gap보다 작으면 두 노드를 u 방향으로 벌린다.

| 관계 | 출발 → 도착 | u | 적용 슬라이더 |
|---|---|---|---|
| 포함 (두 종류) | 부모 → 자식 | (0, 1) 아래 | 구조 중력 |
| 선행 | 앞 → 뒤 | (1, 0) 오른쪽 | 흐름 중력 |
| 합류 | 모이는 쪽 → 합류 대상 | (1, 0) 오른쪽 | 흐름 중력 |
| 원인 | 원인 → 결과 | (1, 0) 오른쪽 | 흐름 중력 |
| 참조 | | 없음 | 없음 |

d3-force를 쓰는 경우 사용자 정의 힘 하나로 구현된다.

```js
function forceDirectional(links, config, sliders) {
  function force(alpha) {
    for (const l of links) {
      const c = config[l.type];
      if (!c || l.inCycle) continue;              // G-18, G-19
      const g = sliders[c.slider];                 // 0 ~ 1
      if (g === 0) continue;                       // G-27
      const dx = l.target.x - l.source.x;
      const dy = l.target.y - l.source.y;
      const along = dx * c.u[0] + dy * c.u[1];
      if (along >= c.gap) continue;                // G-20: 최소 간격 미달일 때만
      const p = (c.gap - along) * c.strength * g * alpha * 0.5;
      l.source.vx -= c.u[0] * p; l.source.vy -= c.u[1] * p;
      l.target.vx += c.u[0] * p; l.target.vy += c.u[1] * p;
    }
  }
  force.initialize = () => {};
  return force;
}
```

이 방식은 스기야마·미스에의 자기장 스프링 모델(1995)과 Dwyer·Koren의 DiG-CoLa(2005)처럼, 힘 기반 배치에 방향 제약을 섞는 기존 연구 계열에 속한다. 새로 발명할 필요가 없는 기법이다.

### 3.3 초기 배치

무작위 배치에서 출발하면 수렴이 느리고, 열 때마다 모양이 달라진다(G-22). 구조에서 초기 좌표를 계산한다.

- **y 초기값**: 포함 깊이 × 간격. 포함 깊이는 부모가 없는 이벤트에서 해당 이벤트까지의 **최장** 경로 길이다. 다중 소속이면 더 깊은 쪽을 따른다.
- **x 초기값**: 흐름 순위 × 간격. 흐름 순위는 흐름 계열 그래프에서 해당 이벤트까지의 최장 경로 길이다. 흐름 관계가 없는 이벤트는 부모들의 x 평균을 쓴다.
- **흔들림**: 같은 좌표에 여러 노드가 겹치지 않도록 이벤트 id를 시드로 한 고정 난수로 작은 흔들림을 준다.

### 3.4 나머지 힘

| 힘 | 내용 |
|---|---|
| 반발 | 모든 노드 사이. d3 `forceManyBody` |
| 스프링 | 모든 엣지. 참조는 다른 엣지보다 약하게 |
| 충돌 | 노드 반지름 + 여백. d3 `forceCollide`. 큰 노드가 겹치지 않게 |
| 중심 | 약한 중심 복귀. 관계 없는 이벤트가 화면 밖으로 흩어지지 않게 |

## 4. 예상 이슈와 대안

### 4.1 흐름 계열의 교차 순환

**가장 중요한 이슈다.** 현재 구조 규칙은 관계 종류별로 순환을 금지한다. 그러나 "A가 B를 선행한다"와 "B 때문에 A가 생겼다(원인)"는 각각 규칙을 지키면서도 합치면 순환이 된다. 흐름 중력은 선행·합류·원인을 모두 오른쪽 방향으로 밀기 때문에, 이런 순환이 있으면 A는 B의 왼쪽으로, B는 A의 왼쪽으로 가려 하며 두 노드가 계속 떨린다.

**처리**: 흐름 계열 엣지를 모아 강결합 요소를 찾고(Tarjan 알고리즘, 선형 시간), 크기가 2 이상인 강결합 요소 안의 엣지에 `inCycle` 표시를 해서 방향 중력에서 뺀다. 해당 엣지는 호버 시 "순환 구간" 표시를 한다. 데이터가 바뀔 때마다 다시 계산한다.

### 4.2 대규모 렌더링과 시뮬레이션 성능

SVG는 노드 1,000~2,000개 부근에서 눈에 띄게 느려진다.

- 반발력 계산은 d3 `forceManyBody`의 Barnes-Hut 근사(`theta`)를 쓴다(G-25).
- 노드가 많아지면 렌더링을 Canvas 2D로, 더 많아지면 WebGL(sigma.js, PixiJS 등)로 바꾼다. 렌더링 계층을 시뮬레이션과 분리해 두면 교체가 쉽다.
- 시뮬레이션을 Web Worker에서 돌리고 좌표만 메인 스레드로 넘기면, 계산 중에도 화면 조작이 끊기지 않는다.

### 4.3 긴 사슬로 인한 화면 이탈

선행 사슬이 길고 포함 깊이도 깊으면 그래프가 가로세로로 모두 길어진다.

- 방향 중력은 최소 간격만 보장하고 상한이 없으므로(G-20), 간격이 필요 이상 벌어지지는 않는다. 그래도 사슬 길이만큼은 길어진다.
- 수렴 후 전체 맞춤 확대를 한 번 실행한다.
- 사용자가 중력을 낮추면 배치가 압축된다(G-27). 탐색 중에는 약하게, 구조를 볼 때만 강하게 쓰는 사용 방식을 기본으로 안내한다.

### 4.4 다중 소속 노드의 긴 선

두 부모가 서로 멀리 있으면 자식 노드가 중간에 걸리면서 두 포함 선이 길어진다. 이것은 오류가 아니라 "소속이 멀리 떨어진 두 곳에 걸쳐 있다"는 정보다. 분신으로 해결하지 않는다(G-06).

### 4.5 라벨 과밀

노드가 많으면 이름이 겹친다.

- 확대 배율에 따라 라벨 표시 기준을 바꾼다. 멀리서는 반지름이 큰 노드만, 가까이 가면 전부 표시한다.
- 호버하거나 선택한 노드와 그 이웃의 라벨은 배율과 무관하게 항상 표시한다.

### 4.6 데이터 변경 시 재배치

다른 화면에서 이벤트나 관계가 바뀌면 그래프도 바뀌어야 한다.

- 기존 노드의 좌표는 유지하고, 시뮬레이션을 낮은 온도로 다시 가열한다. 전체를 처음부터 다시 배치하면 사용자가 보던 위치를 잃는다.
- 새 노드는 부모 근처에서, 부모가 없으면 흐름 이웃 근처에서, 둘 다 없으면 중심 근처에서 생성한다.

### 4.7 좌표 저장 정책

**대안 1 (저장하지 않음)**: 결정적 초기 배치(3.3)만으로 매번 같은 모양이 나오므로, 좌표를 저장하지 않아도 재현성이 있다. 가장 단순하다.

**대안 2 (사용자별 뷰 상태로 저장)**: 사용자가 끌어서 고정한 노드만, 이벤트·배치와 무관한 사용자별 뷰 상태 테이블에 저장한다. 협업 공유 문서에는 넣지 않는다(G-05).

**제안**: 1차는 대안 1로 시작한다. 사용자 요구가 확인되면 대안 2를 추가한다. 어느 경우에도 G-03은 지킨다.

### 4.8 관계 없는 이벤트

포함도 관계도 없는 이벤트는 반발력만 받아 가장자리로 밀려난다. 중심력으로 화면 안에 붙잡아 두고, "관계 없는 이벤트 숨기기" 필터를 둔다.

## 5. 완료 판정

아래 질문에 전부 "그렇다"로 답할 수 있어야 완료다.

1. 부모가 둘인 이벤트가 노드 하나로 그려지고, 포함 선이 둘 들어오는가?
2. 두 중력을 모두 0으로 두면 방향성 없는 순수 힘 기반 배치가 되는가?
3. 구조 중력만 켜면 부모가 자식보다 위로, 흐름 중력만 켜면 앞선 이벤트가 뒤따르는 이벤트보다 왼쪽으로 정렬되는가?
4. 참조 선은 어느 중력에서도 방향이 강제되지 않는가?
5. 흐름 계열에 교차 순환이 있는 데이터를 넣어도 시뮬레이션이 수렴하는가?
6. 가장 큰 노드가 하위 이벤트가 가장 많은 이벤트인가? 트랙이 보드보다 크게 나오지 않는가?
7. 같은 데이터를 두 번 열면 같은 배치가 나오는가?
8. 그래프 뷰에서 무엇을 해도 이벤트, 포함, 배치, 관계 데이터가 바뀌지 않는가?
9. 그래프 뷰 코드 안에 역할 이름(보드, 트랙, 카드, 태스크)으로 분기하는 곳이 없는가?
